PROJECT REPORT NOTES

Project at a glance

A concise report-ready overview of the problem, design, and learning outcomes.

01 / ABSTRACT

Abstract

The Flight Management and Reservation System is a local web application for viewing flights, booking seats, managing reservations, and maintaining a flight schedule. It combines a responsive HTML, CSS, and JavaScript interface with a Python HTTP bridge and a C++17 backend. Flight and booking records are stored in text files. Linear search finds route and airline matches, binary search looks up a flight ID after preparing an ID-sorted copy, and bubble, selection, and merge sort demonstrate different ways to order flights. Booking and cancellation update persisted seat counts, making the algorithms visible in a practical application rather than isolated examples.

02 / PROBLEM

Problem statement

Small flight reservation applications need to locate flights, compare schedules, maintain seat inventory, and store booking history reliably. This project addresses those tasks while illustrating how searching and sorting algorithms operate on flight records. It also needs to reject invalid requests and keep flight and booking files consistent when a reservation is created or cancelled.

03 / OBJECTIVES

Objectives

  • Represent flights and bookings as structured records.
  • Apply linear and binary search to flight lookup.
  • Compare bubble, selection, and merge sorting.
  • Connect algorithm results to booking and admin workflows.
  • Persist records and validate seat changes.
04 / METHODOLOGY

Proposed methodology

  1. Load pipe-delimited flight or booking records from files.
  2. Validate the requested action and its input fields.
  3. Run the appropriate C++ search or sort algorithm.
  4. For mutations, update records and write through a temporary file.
  5. Return JSON through the Python bridge to the browser UI.
  6. Test normal, boundary, and invalid cases using isolated data.
05 / REQUIREMENTS

Hardware & software

Hardware: A basic laptop/desktop, dual-core processor, 4 GB RAM, and a few hundred MB of free storage are sufficient for this small local application.

Software: Windows 10/11, Python 3.8+, a C++17 compiler such as MinGW-w64 g++, and a modern browser. No third-party Python packages or frontend build system are needed.

06 / CONCEPTS

DSA concepts used

  • Vectors (dynamic arrays) to hold flight and booking records.
  • Linear search for partial text and route matches.
  • Insertion sort as preparation for binary search by flight ID.
  • Binary search over sorted flight IDs.
  • Bubble sort for ascending ticket price.
  • Selection sort by date and departure time.
  • Recursive merge sort for ascending flight duration.
07 / TRADE-OFFS

Advantages & limitations

Advantages: Simple local setup, visible algorithm traces, persistent file storage, input validation, and practical seat-inventory updates.

Limitations: Text files and a single-user local server are intended for a classroom demo, not concurrent production traffic. Binary ID lookup currently includes insertion-sort preparation. The admin screen has no authentication. Records are small, so there is no database index or distributed deployment.

08 / NEXT STEPS

Future scope

  • Use a database with indexes and transactional updates.
  • Add user/admin authentication and authorization.
  • Support multiple passengers per booking and richer ticket details.
  • Add route/date availability filters and fare comparison.
  • Use persistent sorted indexes for repeated flight-ID lookups.
  • Add automated UI tests, deployment, and accessibility review.
09 / CONCLUSION

Conclusion

The project demonstrates how core DSA techniques can support everyday flight-search tasks. Linear search handles flexible matching, binary search illustrates lookup on ordered IDs, and the three sorting methods arrange results by useful travel criteria. A file-backed C++ service connects these concepts to real booking, cancellation, and schedule-management flows. The interactive DSA Lab makes the data, intermediate steps, output, and complexity available for a classroom explanation. The system is a learning prototype and a foundation for future improvements, rather than a production airline service.

Merge SortFlight durationBest/average/worst O(n log n)O(n) auxiliary + O(log n) stack

The binary-search phase is O(log n), but this implementation insertion-sorts a copy for each lookup. Its complete lookup therefore takes O(n²) in the average and worst case; if input is already sorted, insertion-sort preparation is O(n).
